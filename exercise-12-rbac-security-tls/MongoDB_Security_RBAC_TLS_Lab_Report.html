1. Executive Summary & CIA Triad Defense Framework

Database security encompasses technical safeguards, administrative policies, and cryptographic controls designed to protect data assets against unauthorized access, corruption, tampering, and denial-of-service. This lab implements a defense-in-depth security model for MongoDB mapped directly against the CIA Triad:

  • Confidentiality (Data Protection & Privacy): Restricting access exclusively to authenticated principals via SCRAM-SHA-256 Authentication, enforcing least-privilege Role-Based Access Control (RBAC), providing fine-grained privacy via Aggregation Views with Field-Level Redaction ($$REMOVE and SSN masking), and encrypting data over the wire using TLS/SSL Encryption.
  • Integrity (Data Accuracy & Trust): Guaranteeing that data cannot be altered by unauthorized users through fine-grained collection privileges, schema validation, and digital certificate validation (X.509 PKI).
  • Availability (Reliability & Uptime): Supporting operational continuity through distributed sharding, query routing via mongos, and high-availability replica sets with automated failover.

2. Lab 12.1: Authentication and Least-Privilege RBAC

2.1 Objective & Strategy

The objective is to eliminate default unauthenticated access by starting mongod with --auth, provisioning a central administrative account, and configuring least-privilege custom roles. In accordance with the principle of least privilege, applications must never connect as broad administrative accounts; instead, roles grant only the exact actions required on targeted namespaces.

3. Activity 12.1: Field-Level Redaction via Views

3.1 Problem Statement & Solution Architecture

Organizations frequently store employee records containing sensitive Personally Identifiable Information (PII) such as Social Security Numbers (SSN) and compensation details (salary). Providing application developers or general staff with access to this data violates privacy mandates (e.g. GDPR, HIPAA, SOC 2).

Instead of creating duplicate, synchronized collections—which introduces data inconsistency and maintenance overhead—MongoDB provides Read-Only Aggregation Views (db.createView()). The view acts as an automated virtual layer that applies a deterministic aggregation pipeline:

  • salary: "$$REMOVE": Completely strips the compensation field from the output payload.
  • ssn: { $concat: ["***-**-", { $substrCP: ["$ssn", 7, 4] }] }: Partially masks the SSN to preserve utility for verification while protecting identity.
Python/PyMongo: Creating the Redacted Aggregation View and Role-Based Separation
pipeline = [ { "$project": { "_id": 0, "empId": 1, "username": 1, "name": 1, "email": 1, "department": 1, "role": 1, "ssn": { "$concat": [ "***-**-", { "$substrCP": ["$ssn", 7, 4] } ] }, "salary": "$$REMOVE" } } ] # Create view db.command("create", "employees_safe", viewOn="employees", pipeline=pipeline) # Grant HR role full access to raw collection; grant staff role access ONLY to the view admin_db.command("createRole", "hr_role", privileges=[ {"resource": {"db": "hr_db", "collection": "employees"}, "actions": ["find", "insert", "update"]} ], roles=[]) admin_db.command("createRole", "non_hr_role", privileges=[ {"resource": {"db": "hr_db", "collection": "employees_safe"}, "actions": ["find", "aggregate"]} ], roles=[])

4. Lab 12.2: TLS / Encryption-in-Transit Setup

4.1 Threat Model & Cryptographic Purpose

While RBAC protects data at the database logical boundary, unencrypted TCP connections expose sensitive credentials, session tokens, and query payloads to network sniffing and Man-in-the-Middle (MitM) attacks. TLS (Transport Layer Security) guarantees:

  1. Confidentiality: Encrypts all frames in transit using strong symmetric ciphers (e.g. AES-256-GCM).
  2. Authentication: Cryptographically validates server identity via X.509 digital certificates signed by a trusted Certificate Authority (CA).
  3. Integrity: Prevents alteration or replay of packets using Message Authentication Codes (HMAC).

4.2 Public Key Infrastructure (PKI) Architecture & OpenSSL Generation

A multi-tier X.509 certificate chain was engineered for the MongoDB deployment:

  • Root CA (ca.crt): Self-signed CA generated with RSA 4096-bit private key.
  • Server Certificate (server.crt): Signed by the CA, bundling Subject Alternative Names (SAN) for DNS:localhost, DNS:mongodb, and IP:127.0.0.1 to prevent hostname validation errors.
  • Server PEM (server.pem): Concatenated private key and signed certificate, required by mongod.
  • Client Certificate (client.pem): Generated for mutual TLS (mTLS) client authentication.
Bash / OpenSSL: Certificate Authority & Server Key Generation with SAN
# 1. Root Certificate Authority (CA) openssl genrsa -out ./tls/ca.key 4096 openssl req -new -x509 -days 365 -key ./tls/ca.key -out ./tls/ca.crt -subj '/CN=MongoDB-CA/O=NoSQL-Lab' # 2. Server Key & CSR openssl genrsa -out ./tls/server.key 4096 openssl req -new -key ./tls/server.key -out ./tls/server.csr -subj '/CN=localhost' # 3. Sign Server Cert with Subject Alternative Names (SAN) openssl x509 -req -days 365 -in ./tls/server.csr -CA ./tls/ca.crt -CAkey ./tls/ca.key -CAcreateserial \ -out ./tls/server.crt -extfile <(echo "subjectAltName=DNS:localhost,DNS:mongodb,IP:127.0.0.1") # 4. Concatenate server bundle cat ./tls/server.key ./tls/server.crt > ./tls/server.pem chmod 600 ./tls/server.pem

4.3 Automated Python Certificate Generator (cryptography Library)

To ensure continuous integration and deployment (CI/CD) readiness, certificate management was automated using Python's cryptography library in generate_certs.py. The script builds the complete X.509 chain programmatically:

Python (generate_certs.py snippet)
san = x509.SubjectAlternativeName([ x509.DNSName("localhost"), x509.DNSName("mongodb"), x509.IPAddress(ipaddress.IPv4Address("127.0.0.1")) ]) server_cert = ( x509.CertificateBuilder() .subject_name(subject) .issuer_name(ca_cert.subject) .public_key(server_key.public_key()) .serial_number(x509.random_serial_number()) .not_valid_before(datetime.datetime.now(datetime.timezone.utc) - datetime.timedelta(days=1)) .not_valid_after(datetime.datetime.now(datetime.timezone.utc) + datetime.timedelta(days=365)) .add_extension(san, critical=False) .sign(ca_key, hashes.SHA256()) )

4.4 Server Launch & Negative Enforcement Test

MongoDB was started enforcing strict TLS connections:

mongod --fork --logpath /var/log/mongodb_tls.log --dbpath /data/db_tls --port 27100 \ --tlsMode requireTLS --tlsCertificateKeyFile ./tls/server.pem --tlsCAFile ./tls/ca.crt
Negative Enforcement Proof: Unencrypted Traffic Rejected
Executing an unencrypted connection attempt via mongosh --port 27100 --eval 'db.runCommand({ping:1})' results in immediate disconnection:
MongoServerSelectionError: connection closed / SSL handshake failed on port 27100.
Conclusion: Unencrypted plaintext traffic is 100% blocked, closing the network eavesdropping attack surface.

6. Conclusion & Production Security Hardening Checklist

This laboratory demonstrated end-to-end configuration of enterprise MongoDB security:

  1. Least Privilege RBAC: Replaced monolithic privileges with granular, resource-scoped roles, preventing accidental data leakage and unauthorized modifications.
  2. Field-Level Redaction Views: Masked PII and excluded sensitive financial data dynamically without maintaining fragile data duplicates.
  3. Cryptographic In-Transit Protection: Enforced TLS with custom X.509 PKI, validating both server authenticity and wire-level confidentiality.
  4. Continuous Delivery Containerization: Standardized the complete environment inside a Docker container published to Docker Hub for grading.
Production Hardening Recommendations
In production environments, complement these controls with: (1) Key Management Service (KMS) integration with WiredTiger Encryption-at-Rest; (2) Enterprise Auditing for compliance change logs; (3) Mutual TLS (mTLS) with x.509 Authentication to replace static passwords; and (4) IP Whitelisting / VPC peering restrictions.
